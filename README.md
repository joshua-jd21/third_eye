# Still & Motion — artist portfolio

An editorial, monochrome portfolio for a multidisciplinary artist working as film
director, cinematographer, visual artist and photographer. Typography-led, square
edges, fine rules, generous negative space, no decorative animation. The work is
meant to carry the page.

The site is content-driven: **replace images in `public/images/`, edit the files in
`src/content/`, paste Vimeo URLs, run `bun run publish`.** No layout work is needed
per project, and no page has to be designed or routed by hand.

For the artist-facing instructions (image sizes, adding a project, Vimeo privacy),
see **[MEDIA-GUIDE.md](./MEDIA-GUIDE.md)**. This file is for whoever inherits the
code.

There is no database, no authentication, no payment processing, no contact-form
backend and no newsletter integration — deliberately. The contact page is a
`mailto:` link. Nothing here should be described to the owner as existing.

## Commands

```bash
bun install          # dependencies
bun run dev          # Vite dev server (port 3000 if free; picks another if not)
bun run build        # production build → dist/client + dist/server
bun run start        # run the built site: bun run serve.ts (0.0.0.0:3000)
bun run publish      # install + build + restart the server on port 3000, then
                     # poll until it answers; safe to re-run, takes over the port
bun run format       # bun fmt .
```

`bun run publish` runs `publish.sh`, which builds in the foreground so errors
surface, then starts `serve.ts` detached with `setsid` and waits up to ten seconds
for an HTTP response. If it prints "published, but the server isn't responding",
read `.run/server.log`.

## Content: where it lives and how components read it

Everything the site renders comes from `src/content/`. No component hard-codes a
title, a path, a credit or a link — if you find yourself typing a project name into
a component, it belongs in the content layer instead.

**`src/content/types.ts`** is the contract:

- `ImageAsset` — `{ src, alt, width, height, caption? }`. `width`/`height` are the
  file's intrinsic size and are rendered onto the `<img>` so space is reserved and
  nothing shifts while images load. `alt` is required by the type.
- `Project` — required: `slug`, `title`, `year`, `role`, `category`, `thumbnail`,
  `poster`. Optional: `hero`, `summary`, `description`, `vimeoUrl`, `stills`,
  `behindTheScenes`, `credits`, `links`, `featured`.
- `CATEGORIES` — the eight category slugs (`direction`, `cinematography`, `film`,
  `commercial`, `music-video`, `photography`, `visual-art`, `other`) with their
  display labels; `categoryLabel()` maps slug → label.
- `ArchiveImage` — an `ImageAsset` plus `caption` and `year`.

**`src/content/artist.ts`** exports `siteUrl` and the `artist` object (name, title,
location, shortBio, bio paragraphs, statement, background, portrait, email,
availability, socials, selectedCredits). Every field is a labelled placeholder.
Sections that read these values hide themselves when the value is empty: an empty
`statement` or `location` string, or an empty `background` / `selectedCredits` /
`socials` array, removes the section rather than leaving a heading with nothing
under it.

**`src/content/projects.ts`** holds `const PROJECTS: Project[]` and exports:

| Export | Used by | Behaviour |
| --- | --- | --- |
| `projects` | home page count, `/work`, sitemap | the catalogue in running order |
| `getProjectBySlug(slug)` | `/work/$slug` loader | throws `notFound()` upstream when missing |
| `getFeaturedProject()` | home page | first entry with `featured: true`, else `PROJECTS[0]` |
| `getSelectedWork()` | home page | catalogue order, featured project excluded, first `SELECTED_WORK_COUNT` (6) |
| `getAdjacentProjects(slug)` | project page | previous/next in catalogue order, wrapping at both ends |
| `getCategoryFacets()` | `/work` filters | only categories that have projects, with counts |
| `getProjectsByCategory(slug)` | `/work` | filter, or the whole catalogue when `null` |
| `toCategorySlug(value)` | `/work` search param | narrows an arbitrary string to a known slug |
| `SELECTED_WORK_COUNT` | home page | `6` |

**Ordering rule:** the `projects` array *is* the running order everywhere — home
Selected Work, `/work`, prev/next, sitemap. There is no separate sort key; reordering
means moving the object. `archive` array order is the visual-archive order.

**`src/content/archive.ts`** — six images, each keeping its own aspect ratio. The
home page composes them into a fixed rhythm (wide / narrow / offset) that repeats
every six slots, so four to eight entries look best.

## Routing

File-based, via TanStack Router. A file in `src/routes/` *is* a URL:

| File | URL |
| --- | --- |
| `routes/__root.tsx` | the HTML shell: `<head>`, fonts, header, `<main>`, footer, 404 |
| `routes/index.tsx` | `/` |
| `routes/work/index.tsx` | `/work` (and `/work?category=<slug>`) |
| `routes/work/$slug.tsx` | `/work/<slug>` — one dynamic route for every project |
| `routes/about.tsx` | `/about` |
| `routes/contact.tsx` | `/contact` |
| `routes/sitemap[.]xml.ts` | `/sitemap.xml` (server route, generated) |
| `routes/robots[.]txt.ts` | `/robots.txt` (server route, generated) |

**Adding a project never means adding a route.** `/work/$slug` is a single dynamic
route whose loader calls `getProjectBySlug(params.slug)`; an unknown slug throws
`notFound()` and renders the route's `notFoundComponent`. A new object in
`projects.ts` therefore appears at `/work/<slug>`, in `/work`, in prev/next and in
`sitemap.xml` with no routing changes at all.

`src/routeTree.gen.ts` is generated by the router plugin on dev/build and is
gitignored — never edit it by hand.

**Filtering is URL-driven.** The `/work` filters are real `<a href="/work?category=…">`
anchors, not buttons: the result set is derived from the search param in
`validateSearch`, so filtering works with JavaScript disabled and every filtered view
is a shareable, back-button-friendly URL. Only categories with at least one project
are listed, and the active one carries `aria-current="page"`.

**Optional sections hide themselves.** On the project page, `stills`,
`behindTheScenes`, `credits` and `links` render only when the array is non-empty;
`description` renders only when present. The Vimeo player, however, always renders —
it degrades to the poster (see below).

## The Vimeo player

`src/lib/vimeo.ts` is the only place that touches a pasted URL:

- `parseVimeoUrl(input)` → `{ id, hash? } | null`. Accepts `vimeo.com/<id>`,
  `vimeo.com/<id>/<hash>`, `vimeo.com/<id>?h=<hash>`,
  `player.vimeo.com/video/<id>`, `…/channels/<c>/<id>`, `…/groups/<g>/videos/<id>`,
  `…/album/<a>/video/<id>`, `…/showcase/<s>/video/<id>`, a bare numeric id, and
  anything on a `*.vimeo.com` host. Anything else returns `null`.
- `buildVimeoEmbedUrl(ref, { autoplay })` rebuilds the embed `src` from the parsed
  id/hash — **the pasted string never reaches the iframe**. It always sets `dnt=1`
  (do-not-track), `title=0`, `byline=0`, `portrait=0`, and `autoplay=1` only on the
  click path.

`src/components/VimeoPlayer.tsx` renders the poster with a Play button and mounts
the iframe only after a click, so no Vimeo request happens on first paint. With no
URL, or an unparseable one, it renders the poster with no play button — never a
broken iframe. Only if a project has neither a video nor a poster does it show a
labelled empty frame. All shipped `vimeoUrl` values are empty strings; no video id
has been invented.

## Placeholders

All 31 images under `public/images/` are generated SVGs: a light grey field with a
hairline border, the file's label, and its exact pixel size and ratio printed on it.
They are honest stand-ins — no stock photography and no generated film stills.

```bash
bun run scripts/generate-placeholders.ts   # rewrites all 31 files
```

Run it to restore a deleted placeholder or after changing the layout's expectations.
It is idempotent and overwrites whatever is at those paths, so **do not run it once
real photography is in place** unless you intend to reset those files.

Note: the script carries its own copy of the project list (slug, title, thumbnail
dimensions) and of the archive dimensions rather than importing `src/content/`. It
knows nothing about projects added later, and it only ever generates placeholders for
`project-one` and `project-two` stills/BTS. It is a bootstrap tool, not a mirror of
the content layer — keep the two in step by hand if you change either.

## SEO

- **Per-route head.** Every route's `head()` calls `pageHead()` from `src/lib/seo.ts`
  with a title, description, path and optional image. It emits `<title>`,
  `description`, Open Graph (`og:type`, `og:site_name`, `og:title`, `og:description`,
  `og:url`, `og:image`, `og:image:alt`), Twitter card tags and a canonical link.
  The artist's name is appended to the title automatically, once.
- **Canonical/OG URLs are absolute**, resolved against `siteUrl` from
  `src/content/artist.ts`.
- **Project pages** use `summary` as the description, falling back to
  "title — role, year. Category." and use the project poster as the sharing image
  (`og:type=article`).
- **`/sitemap.xml`** is a server route generated from the catalogue at request time:
  `/` (1.0), `/work` (0.9), each project (0.8), `/about` (0.7), `/contact` (0.6),
  cached for an hour. A new project is in it the moment it is added.
- **`/robots.txt`** is a server route that allows everything and points at
  `${siteUrl}/sitemap.xml`.

Two SEO caveats to fix before launch:

1. **`siteUrl` still holds a provisional preview address**, not the production
   domain. Canonical URLs, Open Graph URLs and the sitemap are all built from it, so
   until it is changed to the real origin, search engines and link previews are told
   the wrong address. Change it once the domain is connected, then republish.
2. **The default sharing image is an SVG** (`DEFAULT_SHARE_IMAGE` in
   `src/lib/seo.ts` → `/images/featured/home-hero.svg`). Most social platforms only
   render JPG/PNG, so share previews will be blank or fall back to nothing. Export a
   1200 × 630 JPG and repoint the constant.

## Accessibility and interaction

Semantic landmarks (`header`/`main`/`footer`/`nav`/`article`/`figure`), a skip link,
visible focus styles, `aria-current` on the active filter, `aria-label`s on the
player's play button and on the section landmarks, descriptive alt text on every
image, `min-h-[2.75rem]` targets on the small-caps links, and lazy loading with
reserved intrinsic dimensions. The only animation in the piece is a colour transition
on hover; nothing moves on scroll and nothing depends on motion.

## Deployment

**Current state: the site runs from this workspace on port 3000 behind a preview
address. Production hosting and the custom domain are NOT done.** The steps below
describe what remains; nothing here should be reported to the owner as complete.

### What the app needs at runtime

- A JavaScript runtime that can serve a fetch handler: the built output is
  `dist/client/` (static assets) and `dist/server/server.js` (a portable SSR fetch
  handler). `serve.ts` wraps them in a Bun server on `0.0.0.0:3000` — static files
  first, SSR for everything else — and sets a 255 s idle timeout.
- **No environment variables are required.** There are no secrets, no database
  connection strings and no API keys in this project. Nothing reads `process.env`
  at build or run time.
- The port must be reachable from the internet through whatever reverse proxy the
  host provides; the server binds `0.0.0.0:3000` by design and deliberately ignores
  `PORT`/`HOST` env vars so a stray variable cannot move the site off its address.
- Because `/sitemap.xml` and `/robots.txt` are server routes, a host must run the
  SSR handler — a purely static file host will not serve those two URLs.

### Build output

```bash
bun run build     # → dist/client (hashed assets + public/images)
                  # → dist/server/server.js (fetch handler)
bun run start     # serves both on 0.0.0.0:3000
```

`dist/` and `.run/` are gitignored.

### Hosting

Two paths are prepared:

1. **Any Bun or Node 22 host** that can run a long-lived process: build, then run
   `bun run start`, and point the platform's proxy at port 3000. No configuration
   beyond that.
2. **Vercel**, via `bun run go-live`. `build-vercel.sh` assembles a Build Output API
   v3 bundle in `.vercel/output` (static assets plus a single bundled `render`
   function on `nodejs22.x`), and `go-live.sh` deploys it with `--prebuilt` and
   makes the project public. **This requires a `VERCEL_TOKEN` that only the owner
   can authorise** — it is the owner's own Vercel account, and the deploy is not
   run or claimed here.

### Custom domain and HTTPS

Not done, and it cannot be done without the owner's own account access:

1. The owner chooses where the site is hosted (above) and adds the domain in that
   host's dashboard.
2. At their domain registrar, point DNS at the host — an `A` record (or the host's
   provided target) for the apex domain and a `CNAME` for `www`.
3. The host issues and renews the TLS certificate automatically once DNS resolves;
   no certificate is managed in this repository.
4. **Then** update `siteUrl` in `src/content/artist.ts` to the new origin and
   republish, so canonical URLs, share images and the sitemap follow.

Each of those steps needs the owner's authorisation on their own accounts and has
not been performed.

## Content honesty

The name, professional title, biography, artist statement, selected credits, project
titles, years, roles, descriptions, credits, social links, email address and every
image in this repository are **placeholders**. None of it describes a real artist,
and no award, client, festival selection or deployment claim should be read into it.
They exist so the layout can be reviewed with something in it; they must all be
replaced with the artist's own material before the site is shown to anyone.

## Known issues

Small things found while documenting the code — noted rather than fixed, because
they are outside this pass:

- `siteUrl` points at a provisional preview host, so every canonical URL, OG URL and
  sitemap entry currently names the wrong origin.
- `DEFAULT_SHARE_IMAGE` is an SVG, which most social platforms will not render.
- `scripts/generate-placeholders.ts` duplicates the project list instead of importing
  `src/content/projects.ts`, so it silently goes stale as projects are added.
- `getAdjacentProjects()` wraps at both ends, so a catalogue with a single project
  links "previous" and "next" to itself.
- The project page's prev/next navigation and the `/work` numbering both derive from
  catalogue order, so reordering `projects.ts` changes numbering as well as order —
  intentional, but worth knowing before reordering.
